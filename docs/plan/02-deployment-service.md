## 1. 폐기된 모델과 그 이유

이전 기획은 Laravel Forge형 **컨트롤 플레인**이었다. 고객 서버에 에이전트를 심고, 우리 SaaS가 아웃바운드로 배포·업데이트·모니터링하며, 서버 대수로 과금한다.

**왜 버렸나:**

| 전제 | 클로즈드에서 무너지는 지점 |
|---|---|
| OSS 서버가 무료 유입 깔때기 | 무료 유입이 없다. 깔때기 자체가 사라짐 |
| "1대 무료 → 2대째 유료" | 무료 티어의 목적이 OSS 신뢰였다. 클로즈드에 무료 티어는 그냥 손실 |
| Stripe 셀프서브 결제 | 고객이 계약·조달로 들어온다. 카드 결제할 주체가 아님 |
| 상시 아웃바운드 연결 | **폐쇄망에서 동작하지 않는다.** 금융·공공이 주 타깃인데 이게 치명적 |

마지막 줄이 결정적이다. 컨트롤 플레인은 **고객 서버가 우리에게 상시 연결돼 있어야** 성립한다. 우리가 노리는 세그먼트는 정확히 그게 금지된 곳이다.

**대체 모델:** 상시 연결 대신 **① 오프라인 라이선스 ② 풀(pull) 방식 업데이트 ③ 폐쇄망 번들**.

## 2. 판매 형태

| | 매니지드 | 온프렘 |
|---|---|---|
| 인프라 소유 | 우리(또는 고객 클라우드 계정) | 고객 |
| 운영 주체 | 우리 | 고객 (우리는 지원) |
| 업데이트 | 우리가 콘솔에서 실행 | 고객 운영자가 콘솔에서 실행 |
| 폐쇄망 | 해당 없음 | 흔함 — 번들 반입 |
| 장애 대응 | 직접 접속 | **지원 번들**로만 |

**온프렘이 기본값이라고 생각하는 편이 낫다.** 데이터 주권이 주력 세일즈 포인트이므로, 그걸 사는 고객은 대개 자기 인프라를 고집한다.

## 3. 라이선스 — 집행 수단

### 3-1. 형식

```
notikit.<base64url(payload)>.<base64url(ed25519-signature)>
```

알고리즘을 **페이로드가 고르지 못한다.** JWT류가 `alg: none`으로 우회되는 것과 같은 구멍을 원천 차단한다. 버전 필드만 두고 알고리즘은 코드에 고정.

payload: `customerId`, `customerName`, `expiresAt`(필수), `channel`, `limits{projects, devices, sendsPerMonth}`

`expiresAt`이 **없으면 발급 자체가 실패한다.** 만료 없는 라이선스는 회수 수단이 없다.

### 3-2. 검증 지점

| 지점 | 무엇을 | 실패 시 |
|---|---|---|
| 인스턴스(오프라인) | 서명·만료 | 업데이트 경로만 차단. **발송은 계속** |
| 업데이트 서버 | 서명·만료·고객 식별 | 401(없음) / 403(위조) / 403 + `expiresAt`(만료) |

**만료와 위조를 다른 상태로 둔다.** 만료는 영업이 풀 일이고, 위조는 보안 사건이다.
검증 함수는 `expired`와 `invalid`를 구분해 돌려주고, 인스턴스 콘솔도 다르게 표시한다.

단, **HTTP 상태 코드는 둘 다 403**이고 응답 본문으로만 갈린다(만료 응답에는 `expiresAt`이
실린다). 상태 코드만 보는 모니터링을 붙이면 두 사건이 한 덩어리로 보인다.

### 3-3. 한도는 표시만, 집행 안 함

`limits`는 콘솔에 보이지만 **강제하지 않는다.** 의도적이다.

초과했다고 푸시를 막으면, 그 순간 고객사 최종 사용자에게 알림이 안 간다. 계약 초과는 청구서로 풀 문제다. 서비스를 인질로 잡으면 **초과분보다 큰 사고**가 난다.

> 향후 집행이 필요하면 "차단"이 아니라 "콘솔 경고 + 우리 쪽 알림"으로 간다.

## 4. 업데이트 — 풀(pull) 방식

```
고객 인스턴스 ──(라이선스 Bearer)──▶ 업데이트 서버 (우리)
      │                                      │
      │◀───── 버전 + 이미지 다이제스트 ◀──────┘
      ▼
  update_jobs (DB) ──▶ 업데이터 사이드카 ──▶ 컨테이너 교체
```

**클라이언트가 버전을 고르지 않는다.** 고르게 두면 건너뛰면 안 되는 마이그레이션을 건너뛰거나, 만료된 구독으로 걸어 들어간다.

### ⚠️ 그런데 **채널**은 고객사가 고를 수 있다

버전은 막았는데 채널은 안 막혔다.

- 고객사 박스의 `.env`가 `NOTIKIT_UPDATE_CHANNEL`을 정하고, 인스턴스가 그 값을 쿼리로 보낸다
- 서버는 `override.channel ?? requestedChannel ?? license.channel ?? "stable"` 순으로 고른다
- `customers.json`에 그 고객 override가 **없으면 요청 채널이 라이선스 채널을 이긴다**

즉 stable 계약 고객이 `.env` 한 줄로 **beta 릴리스를 끌어올 수 있다.** 위에서 버전 선택을
막은 논거가 채널 축에서 그대로 뚫린다.

고칠 곳은 문서가 아니라 서버다 — `license.channel`을 `requestedChannel`보다 **앞에** 두면
된다. 그때까지는 베타 고객마다 `customers.json`에 명시적 override를 넣어 두는 것이
유일한 방어다.

**콘솔은 Docker 소켓을 만지지 않는다.** 소켓은 호스트 root와 같다. 웹에 노출된 컨테이너가 그걸 쥐면 웹 취약점 하나가 곧 호스트 장악이다. 콘솔과 업데이터는 **DB의 `update_jobs` 행으로만** 대화하고, 소켓은 포트를 열지 않는 사이드카만 쥔다.

**순서: 받기 → 백업 → 마이그레이션 → 교체 → 확인.** 마이그레이션이 실패하면 구버전 컨테이너가 계속 서빙한다. 교체를 먼저 하면 실패 시 새 코드와 옛 스키마가 만난다.

**백업은 마이그레이션이 있는 릴리스에서만 뜬다.** 없는 릴리스는 건너뛴다 — 되돌릴 것이
컨테이너뿐이라 자동 롤백으로 충분하기 때문이다(아래).

**자동 롤백은 마이그레이션이 없는 릴리스에만.** 스키마가 이미 움직였으면 컨테이너만 되돌려도 복구가 아니다 — 백업에서 복원해야 한다.

### 4-1. 배포 제어 (`customers.json`)

```json
{
  "acme":    { "pin": "1.1.0" },
  "beta-co": { "channel": "beta" },
  "gone":    { "blocked": true }
}
```

**`pin`이 이 파일의 존재 이유다.** 특정 릴리스에 문제가 생겼을 때 **그 고객만** 세워 둘 수 있다. 이런 수단이 없으면 사고 시 할 수 있는 일이 "전체 배포 중단"뿐이다.

## 5. 폐쇄망

금융·공공에서는 사실상 기본값이다.

1. CI 아티팩트에서 `notikit-<버전>-airgap.tar` + `.sha256` + `.tar.json`
2. 고객 박스의 `./bundles/` 에 반입
3. 콘솔 **업데이트** 화면에 나타남 → 설치

**브라우저 업로드를 쓰지 않는다.** 번들이 수 GB라 HTTP 업로드는 깨질 지점이 너무 많고, 어차피 파일은 이미 그 박스에 있다.

**`.sha256`이 없으면 설치를 거부한다.** USB와 사람 손을 거쳐 온 것을 검증 없이 설치하면 무엇을 설치하는지 모르는 채로 설치하는 것이다.

## 6. 요금

셀프서브가 아니므로 공개 가격표를 두지 않는다. 견적 기준만 정리한다.

```
도입비(1회)      : 설계 + 설치 + SDK 통합 + UAT       — 규모별
라이선스(연간)   : 인스턴스당. 한도(프로젝트/디바이스/월 발송)로 티어 구분
유지보수(연간)   : 통상 도입비의 10~15%/년
```

**가격 기준선:** 비교 대상이 OSS가 아니라 **OneSignal/Airship 같은 상용**이다. "무료 대비 얼마"가 아니라 "상용 SaaS 대비 온프렘 프리미엄"으로 잡는다. 데이터 주권 요건이 있는 고객은 애초에 가격이 1순위가 아니다.

**전송량은 한도에 넣되 과금 축으로는 약하다.** 고객이 자기 FCM으로 보내므로 **우리 비용이 아니다.** 발송량 과금은 우리가 안 쓰는 자원에 값을 매기는 것이라 방어하기 어렵다. 프로젝트 수·디바이스 수가 더 정직한 축이다.

## 7. 소스 보호 — 기대치

원본 TypeScript는 이미지에 들어가지 않는다. 소스맵은 내용이 비어 있어 복원되지 않고, 빌드 마지막에 지운다.

**하지만 번들된 서버 JavaScript는 들어간다.** 압축돼 있을 뿐 로직이다. 고객 박스에서 돌리는 이상 막을 방법이 없다.

난독화·bytenode는 **하지 않는다.** 스택트레이스를 망가뜨려 온프렘 장애 대응 비용만 몇 배로 만들고, 작정한 사람은 못 막는다. 우리가 고객 박스에 들어갈 수 없는 상황에서 스택트레이스를 버리는 건 자해다.

방어선은 **계약 + 라이선스 + 회수 가능한 레지스트리 계정.** 정말 내줄 수 없는 로직이 있다면 온프렘에 두지 말고 우리 서버에 남긴다.

## 8. 리스크 & 완화

| 리스크 | 완화 |
|---|---|
| **영업 부재** — 유입 깔때기 없음 | 완화책 없음. 초기 레퍼런스 확보가 사업의 전부 |
| **비밀키 분실** | 신규 발급 불가. 오프라인 백업 |
| **공개키 교체** | **전 고객 동시 무효.** 하지 말 것 |
| 이기종 환경 | "Linux + Docker"로 지원 범위 제한, compose 표준화 |
| 온프렘 장애 진단 | 지원 번들(값 없이 설정 유무만) + 업데이트 로그 |
| 업데이트 중 발송 유실 | ⚠️ **미해결** — graceful shutdown 미구현. §9 |
| 마이그레이션 실패 | 마이그레이션 릴리스는 사전 덤프 강제, 마이그레이션 전 교체 금지 |

### ⚠️ 미해결: graceful shutdown

업데이트는 컨테이너를 교체한다. 지금 `web`이 `process-queue` 중에 SIGTERM을 받으면 **처리 중이던 발송이 유실될 수 있다.** `worker.mjs`는 얇은 폴러라 위험이 작지만 `web`은 아니다.

무인 업데이트를 파는 이상 이건 기능이 아니라 **전제 조건**이다. 야간 자동 업데이트를 계약에 넣기 전에 해결해야 한다.

## 9. 로드맵

배포 메커니즘(라이선스·업데이트 서버·업데이터·폐쇄망·릴리스 CI)은 **완료**다.

첫 고객 전 착수 순서는 **[README 「첫 고객 전 착수 순서」](README.md#첫-고객-전-착수-순서-단일-출처)가 단일 출처**다. 여기서 중복 기술하지 않는다 — 이전 개정에서 이 로드맵과 04의 체크리스트가 서로의 차단 항목을 몰라 결론이 갈렸다.

이 문서가 추가로 책임지는 항목:

- **채널 오버라이드 차단** (§4) — `license.channel`을 요청 채널보다 앞에 두기
- **갱신 절차** — 만료 임박 탐지(폐쇄망은 우리가 알 수 없다), 통지 주체, 새 라이선스 주입 방법, 갱신 실패 시 처리. **현재 전무하다**
- **해지·이탈 절차** — 데이터 반출(GDPR export는 미구현), 인스턴스 폐기, 암호화 키 처리, 계약 종료 후에도 도는 설치본에 대한 보안 패치 의무 범위. 온프렘 조달에서는 계약 필수 조항이다
- **SLA 정의** — §6에서 유지보수로 팔고 있으나 대응/복구 시간·심각도 등급·커버리지 시간이 정의돼 있지 않다. 온프렘은 고객 인프라인데 **무엇을 보증하는지**부터 정해야 한다
