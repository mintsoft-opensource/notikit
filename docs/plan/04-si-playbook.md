# 구축(SI) 플레이북

> 클로즈드 상용에서 **이것이 주 판매 경로다.** 이전 기획에서는 OSS → BYOC 구독 위의
> 최상단 티어였지만, 무료 유입이 사라진 지금은 **거의 모든 계약이 여기로 들어온다.**
> 고접점·고단가·저확장. **표준화·반복가능**하게 만드는 게 마진의 핵심.
> (← [README](README.md) · [02-deployment-service.md](02-deployment-service.md) · 절차는 [../DISTRIBUTION.md](../DISTRIBUTION.md))
>
> 개정일: 2026-09-11

## 1. 진행 7단계 (산출물)

| 단계 | 할 일 | 산출물 |
|---|---|---|
| **1. 발굴·요구분석** | 플랫폼·볼륨·기존인프라(FCM/APNs)·유저모델·규제(ISMS/GDPR)·**폐쇄망 여부** | 요구정의서, 사이징 |
| **2. 견적·계약** | 범위·일정·수용기준·**라이선스 기간과 한도** | SOW + 견적 + 계약(변경관리 조항) |
| **3. 설계** | 환경 맞춤(서버/DB/도메인/TLS), 통합설계(인증→identify, API키, SDK), 마이그레이션 | 아키텍처·통합·보안 검토서 |
| **4. 환경 구축** | compose 설치, DB, 자격증명, **라이선스 주입**, 백업·모니터링·TLS | 구축 환경 + 구성문서 |
| **5. 통합** | 앱 SDK 통합(또는 고객팀 지원), identity·토픽·웹훅 연결 | 통합 완료, 연동 테스트 |
| **6. 테스트·UAT** | 플랫폼별 발송·부하테스트·장애/재시도 → 인수테스트 | 테스트 결과서, UAT 승인 |
| **7. 오픈·인수인계** | 컷오버, 콘솔 교육, **런북**([백업/복구](../BACKUP-RESTORE.md)·[업데이트](../DISTRIBUTION.md)) | 인수인계서 + 유지보수 계약 |

### 1단계에서 반드시 물을 것: 폐쇄망인가

이 질문이 **나머지 전부를 바꾼다.**

| | 인터넷 연결됨 | 폐쇄망 |
|---|---|---|
| 업데이트 | 콘솔에서 클릭 | 번들 반입 후 클릭 |
| 이미지 | 레지스트리 pull | `docker load` |
| 라이선스 | 오프라인 검증(동일) | 오프라인 검증(동일) |
| 릴리스 통지 | 자동 | **사람이 전달** |

라이선스를 오프라인 검증으로 만든 이유가 이것이다. 계약 후에 "사실 폐쇄망입니다"를 듣고 재설계하는 일이 없어야 한다.

## 2. 4단계 체크리스트 (구축)

```bash
# 1) 라이선스 발급 (우리 장비, 비밀키는 여기에만)
NOTIKIT_LICENSE_PRIVATE_KEY_FILE=./license-private.pem \
  node tools/license/issue.mjs issue \
    --customer <id> --name "<고객사명>" \
    --months 12 --projects N --devices N --sends N

# 2) 고객 전용 레지스트리 계정 생성 (계약 종료 시 이 계정만 죽인다)

# 3) 고객 박스
echo "NOTIKIT_IMAGE=<registry>/notikit@sha256:..." > .notikit-image.env
docker compose -f docker-compose.prod.yml up -d
```

**인수인계 전 확인:**
- [ ] `NOTIKIT_ENCRYPTION_KEY` 백업됨 — **분실 시 Firebase 자격증명 전량 복호화 불가**
- [ ] 🔴 **DB 백업 스케줄을 걸었는가** — **기본 제공되지 않는다.** 자동 덤프는 마이그레이션
      있는 업데이트 직전에만 뜬다. 호스트 cron 설정은 [../BACKUP-RESTORE.md](../BACKUP-RESTORE.md) §1
- [ ] **복구를 한 번 해봤는가** — 해보지 않은 백업은 백업이 아니다. 같은 문서 §3
- [ ] 🔴 **`LOG_RETENTION_DAYS` 합의·설정** — purge 는 구현됐지만 **미설정이면 돌지 않는다**(03 §4).
      설정 없이 넘기면 로그가 무한히 자라 디스크를 채우고 코어 테이블까지 세운다
- [ ] **디스크 사용량 감시 + 알림** — purge 가 있어도 런북 필수 항목
- [ ] 라이선스 만료일이 계약 종료일보다 **뒤**인가
- [ ] `NOTIKIT_SELF_UPDATE` — 고객이 직접 업데이트할지 우리가 할지 결정됨
- [ ] 부트스트랩 조직이 **우리 계정**인가 (인스턴스 운영자 권한, 03 §5)

## 3. 계약·과금

```
도입비(1회)      : 설계 + 구축 + 통합 + 테스트 (규모별)
+ 라이선스(연간) : 인스턴스당. 한도로 티어 구분
+ 유지보수(연간) : 통상 도입비의 10~15%/년 (업데이트·장애대응·SLA)
```

- **재발 매출 = 라이선스 + 유지보수.** 도입비 일회성만으론 불안정하다.
- 한국 관행: 구축비 + 유지보수율(10~15%) + 공공은 조달/보안심사(ISMS).
- **라이선스 만료 ≠ 서비스 정지.** 만료되면 업데이트만 막힌다(02 §3-2). 갱신 협상 중에 고객 서비스가 죽지 않는다 — 이걸 계약서에 명시하면 도입 저항이 줄어든다.

## 4. 반드시 피할 함정

**1. 커스텀 포크 지옥** — 고객마다 코어를 갈라 고치면 유지보수 폭탄이다. **config/plugin 확장점**으로 흡수하고, 유용한 커스텀은 본선에 병합한다.

클로즈드에서 이건 **더 위험해졌다.** OSS 시절엔 포크가 고객 저장소에 남아 우리 부담이 아니었지만, 지금은 모든 사본이 우리 책임이다. 고객사 A의 포크에 보안 패치를 적용하는 일이 우리 일이 된다.

**2. 스코프 크립** — SOW 밖은 변경요청(CR) 별도 과금.

**3. 비반복 구축** — **표준 딜리버리 키트**(체크리스트·compose·프로파일·런북)로 반복가능하게. 마진은 여기서 나온다.

**4. 지원 범위 무제한** — 우리는 고객 박스에 못 들어간다. 진단 수단은 **지원 번들**뿐이다(값 없이 설정 유무·마이그레이션·업데이트 로그). 계약서에 "고객이 지원 번들을 제출한다"를 넣지 않으면 전화로 더듬는 시간이 전부 우리 손실이 된다.

**5. 무인 업데이트 약속** — ⚠️ graceful shutdown 미구현(02 §8). 야간 자동 업데이트를 계약에 넣기 전에 해결해야 한다. 지금 약속하면 첫 사고가 첫 고객에서 난다.

## 5. 제품 사다리 (개정)

이전 사다리는 이랬다:

```
OSS(무료 유입) → BYOC 구독(셀프서브) → SI(대형/공공)
```

**지금은 사다리가 아니라 하나의 길이다:**

```
직접 영업 → 구축(SI) → 라이선스 + 유지보수 갱신
                ↓
        표준 키트·플러그인 축적 → 다음 구축 원가↓
```

**리드 소스가 사라졌다.** OSS가 "발견·신뢰"를 대신해 주던 자리가 비어 있다. 그 자리를 채울 수 있는 것:

- **레퍼런스** — 첫 고객 1곳이 다음 고객의 신뢰 담보다. 도입 사례 공개 조건을 1호 계약에 넣을 가치가 있다(가격 할인과 교환해도 남는다)
- **보안 문서** — 아키텍처·데이터 흐름·암호화·ISMS 대응표. 온프렘 고객의 보안 심사는 어차피 통과해야 하고, 미리 만들어 두면 영업 자료가 된다
- **데이터 주권** — 오픈소스가 주던 "숨길 게 없다"는 신뢰를 "데이터가 나가지 않는다"로 대체한다

## 6. 아직 없는 것 (계약서를 쓸 수 없는 공백)

배포 **메커니즘**은 다 돌아간다. 비어 있는 건 **상용 계약 레이어**다. 아래가 없으면
유지보수 계약서를 실제로 작성할 수 없다.

| 공백 | 왜 막히나 |
|---|---|
| **온보딩 end-to-end** | 라이선스 발급 → 레지스트리 계정 → `compose up`에서 끊긴다. **최초 관리자·부트스트랩 조직 생성 절차**, `NOTIKIT_ENCRYPTION_KEY` 생성, TLS·역프록시 담당, Firebase 자격증명 수령·주입, 스모크 테스트가 없다 |
| **갱신** | 만료 시 *동작*만 정의돼 있고 갱신 절차가 없다. 폐쇄망은 만료 임박을 **우리가 알 수 없다** — 달력 관리 주체, 통지 리드타임, 새 라이선스 주입 방법(재시작 필요?)이 전부 미정 |
| **해지·이탈** | 데이터 반출(GDPR export **미구현**), 인스턴스 폐기, 암호화 키 처리, 계약 종료 후에도 도는 설치본의 보안 패치 의무 범위. 온프렘 조달에서 exit plan은 **계약 필수 조항**이다 |
| **SLA** | 유지보수로 팔고 있는데 심각도 등급·커버리지 시간이 없다. 온프렘은 고객 인프라인데 **무엇을 보증하는지**부터 정해야 한다. RTO/RPO 측정법은 [../BACKUP-RESTORE.md](../BACKUP-RESTORE.md) §5 |
| **사이징 표** | 1단계 산출물에 "사이징"이 있으나 디바이스 수·발송량 → CPU/RAM/디스크 표가 없다. 고객이 우리 숫자로 박스를 사야 하므로 견적 전에 막힌다 |
| **폐쇄망 릴리스 통지** | "사람이 전달"로만 적혀 있다. 보안 패치를 누가 며칠 안에 추적·전달할지 없다 |

### ⚠️ 부트스트랩 조직 소유 주체가 충돌한다

위 체크리스트는 "부트스트랩 조직이 **우리 계정**인가"를 확인하라고 한다.
그런데 02는 온프렘 업데이트 주체를 "**고객 운영자**가 콘솔에서 실행"이라고 판다.

`isInstanceOperator()`는 superadmin이거나 **부트스트랩 조직의 owner**만 통과시킨다.
부트스트랩이 우리 것이면 **고객 운영자는 업데이트를 실행할 수 없다.** 파는 것과 코드가
직접 충돌하므로, 매니지드/온프렘 각각에서 부트스트랩을 누가 갖는지 정해야 한다.

## 7. 한 줄

> **요구분석(폐쇄망 확인)→SOW→설계→구축(라이선스 발급)→통합→UAT→인수인계+유지보수** 7단계 표준화.
> **코어 포크 금지**, **도입비+라이선스+유지보수(10~15%)**, **딜리버리 키트로 반복가능**하게.
> 리드는 이제 제품이 아니라 **사람이 만든다.**
