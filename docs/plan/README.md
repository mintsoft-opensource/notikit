## 1. 무엇이 바뀌었나

이전 기획은 **OSS(무료 유입) + BYOC(고객 인프라)** 였다. 두 축 모두 폐기됐다.

| | 이전 | 지금 |
|---|---|---|
| 소스 | 공개(Apache-2.0) | **비공개** |
| 유입 | OSS-led PLG, 개발자 셀프서브 | **직접 영업** |
| 과금 | 서버 대수 구독 | **고객사별 인스턴스 계약** |
| 집행 수단 | Stripe 결제 게이트 | **Ed25519 라이선스 + 레지스트리 계정** |

**이 변경은 유통 전략을 통째로 비운다.** 이전 기획의 리스크 1번이 "유통 실행력(영업→개발자 마케팅 전환)"이었는데, 클로즈드로 가면 그 전환 자체가 없어진다. 원래 실패 원인이었던 **영업 부재가 다시 정면 과제로 돌아온다.** OSS가 대신 해 주던 유입을 이제는 사람이 해야 한다.

이 문서는 그 사실을 숨기지 않는다. 남은 전략은 "제품이 알아서 팔린다"가 아니라 **"적은 수의 고단가 고객을 직접 딴다"** 이다.

## 2. 비전 & 배경
- **MintApp(SaaS)** 운영 경험 있음 → 폭발 못 함. 원인: **영업 부재 + 운영비**.
- 운영비는 **고객사 인스턴스**가 해결한다. 고객이 자기 서버·자기 FCM 비용을 낸다.
- 영업은 **해결되지 않는다.** 클로즈드에는 무료 유입 깔때기가 없다. 이건 완화가 아니라 **감수하는 리스크**다(§8).

## 3. 핵심 차별점 (왜 FCM/경쟁자 대신)
FCM은 **토큰 중심**이라 없는 것 = 우리의 wedge:
1. **유저/계정 identity** — 토큰이 아니라 "유저 X"에게. 계정↔다중기기, 로그인/로그아웃 재매핑
2. **멀티테넌트** — 프로젝트별 Firebase 자격증명 격리·암호화 (에이전시/SI가 여러 앱 대행)
3. **관리 콘솔** — 프로젝트/디바이스/토픽/로그/통계
4. **멀티플랫폼 SDK 풀세트**(웹뷰 포함)
5. **데이터 주권** — 고객 인프라에 전량 적재. 규제산업(금융/공공) 진입, 벤더락인 없음

> **한 줄:** "고객사 인프라에 설치되는 유저중심 푸시 플랫폼 — FCM 릴레이 + 콘솔 + SDK 풀세트."

**주의:** 5번(데이터 주권)이 이제 **주력 세일즈 포인트**다. 오픈소스라는 신뢰 담보가 사라졌으므로, "우리 서버에 데이터가 안 나간다"가 그 자리를 대신해야 한다.

## 4. 시장 & AI 순풍
- 푸시 SW 시장: 정의따라 **$1.8B~$28B**, CAGR **15~27%**.
- **AI 순풍**: 2026 알림/대화량 **3~5배 폭증** 전망, 에이전트가 유저에게 선제 도달 → **identity 레이어 가치 상승**.
- **경계**: "온프렘 + 유저중심"은 전체 시장의 **슬라이스**다. 클로즈드 전환으로 그 슬라이스는 **더 좁아졌다** — 셀프호스트를 찾던 개발자 중 오픈소스를 조건으로 걸던 층이 빠진다. 남는 건 **규제·데이터주권 때문에 온프렘이 필수인 조직**이다.

## 5. 경쟁 지형
- **상용**: FCM(무료·토큰만), OneSignal, Airship/Braze(엔터), Knock/Courier(인프라)
- **OSS**: ntfy·Gotify(경량), Novu·Dittofeed·Laudspeaker(마케팅 지향) — **이제 이들은 경쟁자가 아니라 대체재다.** 우리가 클로즈드이므로, 무료를 원하는 고객은 애초에 우리 고객이 아니다
- **앱빌더**: **nachocode**(노코드 웹뷰→앱, 푸시=얕은 부가기능) — 층위 다름
- **재사용(경쟁 아님)**: 실시간=Centrifugo/Soketi, 배포=Kamal

**포지션 변경:** 이전엔 "오픈소스 OneSignal 대체"였다. 지금은 **"온프렘 OneSignal 대체"** 다. 비교 대상이 OSS 진영에서 상용 진영으로 올라갔고, 그만큼 **기능·지원·SLA 기대치도 올라간다.**

## 6. 비즈니스 모델
```
고객사별 인스턴스 (매니지드 또는 온프렘)
  ├─ 도입비(구축)   : 설계·설치·SDK 통합·UAT
  ├─ 라이선스(연간) : Ed25519 서명 토큰. 만료 시 업데이트 중단(서비스는 계속)
  └─ 유지보수(연간) : 업데이트·장애대응·SLA
```

**핵심 설계 결정 세 가지:**

**① 만료는 서비스를 죽이지 않는다.** 라이선스가 만료되면 **업데이트만** 막힌다. 돌던 인스턴스는 계속 푸시를 보낸다. 계약 분쟁이 곧 고객사 서비스 장애가 되면, 그 사고는 우리 평판으로 돌아온다. 계약은 법무로 풀 문제이지 킬스위치로 풀 문제가 아니다.

**② 라이선스 검증은 오프라인이다.** 폐쇄망 고객은 우리 서버에 전화를 걸 수 없다. 네트워크가 필요한 검증은 거기서 그냥 동작하지 않는다.

**③ 회수 수단은 레지스트리 계정이다.** 계약 종료 시 고객 전용 레지스트리 계정을 죽이면 새 버전을 못 받는다. 이미 설치된 것은 계속 돈다(①과 같은 이유).

상세: [02-deployment-service.md](02-deployment-service.md) · [04-si-playbook.md](04-si-playbook.md)

### ⚠️ 라이선스 표기 불일치 (착수 전 해결)

저장소 루트의 `LICENSE`는 **Apache-2.0 전문**이고, `package.json`은 이렇게 선언한다:

```json
"description": "Notikit — open-source, self-hostable, user-centric push notification toolkit",
"license": "Apache-2.0"
```

Apache-2.0은 **취소 불가능한(irrevocable) 영구 라이선스**다. 이 상태로 코드가 한 번이라도 외부에 나가면 그 사본은 영구히 Apache-2.0이며, 나중에 파일을 지워도 **소급 회수되지 않는다.** 클로즈드 상용 전제가 그 지점에서 무너진다.

고객 인스턴스에 이미지가 나가기 전에 정리해야 한다. 이건 문서 작업이 아니라 **법무 판단이 필요한 결정**이므로 이 문서는 사실만 적고 처리는 별도로 둔다.

## 9. 결론
- **운영비 문제는 풀렸다.** 고객사 인스턴스 + 라이선스 + 업데이트 파이프라인이 다 돌아간다.
- **영업 문제는 안 풀렸다.** 오히려 OSS를 버리면서 유일했던 자동 유입 장치를 없앴다.
- **인수인계 차단 요인이던 `push_logs` purge는 구현됐다.** 남은 차단선은 라이선스 표기다.

### 아직 답이 없는 두 가지 (§6 모델 재검토 필요)

**① 폐쇄망 고객의 회수 수단이 없다.** §6은 "레지스트리 계정을 죽인다"고 했는데, 폐쇄망
고객은 레지스트리에서 받지 않는다. 계정을 죽여도 아무 일도 일어나지 않는다. 실질 수단은
"번들을 주지 않는다"뿐인데, 그건 우리가 능동적으로 안 주는 것이라 계약서 문구가 필요하다.

**② 한도를 과금 축으로 삼았는데 측정할 수 없다.** §6은 한도로 티어를 나눈다. 그런데 한도는
집행하지 않고(의도된 결정), 초과를 우리가 알 경로도 없다 — 원격 모니터링은 폐쇄망에서
동작하지 않는다. **갱신 협상에 쓸 근거 데이터가 없다.** 고객 자기 보고에 의존할지, 콘솔에
경고만 띄우고 넘어갈지 정해야 한다.
